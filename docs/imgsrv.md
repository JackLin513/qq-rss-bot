# 自建图床（喂给 QQ 的 markdown）

2026-10-22 加。代码在 `src/qq_rss_bot/imgsrv.py`。
常驻要点在 [`../CLAUDE.md`](../CLAUDE.md)，这里记来龙去脉。

## 为什么非要有它

生日贺图是**一个偶像一条 markdown**，正文里 `![](url)` 放最多 6 张图。
2026-10-22 真发了两遍，**预热 45 秒和 180 秒，群里都一张图没有**。

根因不是格式、不是尺寸、更不是预热不够：

> **markdown 的图是 QQ 的服务器去下载的。** 它在大陆机房，**够不到
> `pbs.twimg.com`**。

对照实验就在同一个功能旁边：偶像大师 NEWS 那条链路（`multiimage.py`）用
`idolmaster-official.jp` 的 CMS 图，`![](url)` **一直显示得好好的**。
所以「QQ 抓不到境外图」这个说法是错的 —— 它抓得到日本站，**只是抓不到推特**。

结论：贺图必须**我们自己托管一份**。这条路和 `preview.py`（把图下下来 base64
上传，走 `msg_type=7`）是两条完全不同的路，别混。

## 网络：家里两条宽带，只有一条有公网 IP

```
有线宽带（公网 IP）→ 路由器(LAN) → NAS 网口 1
另一条宽带（PPPoE，CGNAT）→ NAS 网口 2
```

- 公网 IP 在**路由器后面**那一侧（NAS 的 LAN 2，`192.168.0.6`）。
- PPPoE 那条是 `100.101.80.44`（`100.64/10` = **CGNAT，不是公网**），
  选它是没用的。

## ⚠️ DDNS 用 DSM 设置里的那个，但两个坑要记住

**2026-10-22 排查出过两个都错的选法**（现在都避开了，留着当判据）：

| DSM 里的选法 | 它干了什么 |
|---|---|
| 「自动」 | 去外部回显服务问 IP，**请求被全局代理接管** → 写进去的是代理出口（日本/香港） |
| 「局域网 2」 | 直接把网卡地址 `192.168.0.6` 写进 A 记录 |

**这两个是「最近几个月都不可达」的真正原因。**「自动」在**关掉全局代理之后是对的**
（实测回显服务和宽带的真实公网 IP 一致），但只要哪天再开回全局代理就又会写错 ——
所以图床突然不可达时，**第一个怀疑对象就是代理**。

`www.jacklin513.top` 和 `jacklin513.synology.me` **都配在 DSM 的 DDNS 里**
（服务商那一栏选 DNSPod / 自定义），两个都会跟着 IP 变，不用另建 CNAME。

⚠️ 但「配了」和「真的在更新」是两件事 —— 判据只有一条：

```bash
dig +short www.jacklin513.top          # 对一下 NAS 的出口 IP
curl -s http://ip.3322.net
```

两个不一样就是 DDNS 没在跑（或者跑起来又被代理带偏了）。图床静默失效时，
这条命令比翻日志快。

## ⚠️ 最后一公里：路由器必须做端口转发（**只能用户本人做**）

DDNS 只保证「域名 → 正确的公网 IP」。**IP 通不等于端口通** —— 入站还要路由器
转发一条：`WAN 18080 → 192.168.0.6:18080`。

- **别转发 80 / 443**：电信入站封这两个（实测外部探测 80/443 一律超时）。
- NAS 的 LAN 2 建议在路由器上**做静态 IP 绑定**，否则重启后地址一变转发就错。

### 怎么读外部探测的结果（2026-10-22 实际读数）

从境外节点 `check-host.net` 探 `183.129.112.13`：

| 现象 | 含义 |
|---|---|
| **`Connection timed out`** | 包被丢了（多半是 ISP 侧拦了，80/443 就长这样） |
| **`Connection refused`** | 有人回 RST —— **路由器上没有这条转发** |
| 正常应答 | 转发通了 |

那天 8092 / 8800 / 7892 三个本机明明在听的端口，**全部 `Connection refused`**
—— 说明路由器一条转发都没有，不是「服务没起」。

## imgsrv 的形态

```
http://<IMGSRV_BASE>/<32 位十六进制 token>/<推文id>.jpg
```

- **每张图一个随机 token**：猜不到、也不能枚举翻别人的图。
- 只认 `^[0-9a-f]{32}$` + 白名单扩展名（jpg/png/gif/webp）；路径穿越在正则这一层
  就断了。目录列表、根路径、大写 token、`.exe` 全部 404（smoke `[4.97.1]` 钉了 6 种）。
- **扩展名按魔数定**（`suffix_of`）—— 推特图不一定是 jpg，URL 后缀经常骗人。
- **TTL 自动删**（`IMGSRV_TTL_DAYS`，默认 7 天）。贺图发完没人再看。
- 端口开不起来（被占 / 没权限）**只打 WARNING，不抛** —— 图床挂了不该拖垮机器人；
  那时 `publish()` 照样写文件，只是没人能取到。
- 只读：HTTP 侧没有任何写入口。**别把它扩成通用 web 服务。**

## 部署要点

1. `.env`：`IMGSRV_BASE=http://<域名>:18080`（空 = 关闭，贺图照发但没图）。
2. `docker-compose.yml` 里 bot 服务发布了 `18080:18080` ——
   **改了要 `up -d`**，`restart` 不会重建容器、端口映射不生效。
3. 路由器：`WAN 18080 → NAS 18080`。
4. DNSPod token + DSM 任务计划（见上）。
5. 验：浏览器/手机 4G 打开一条 `IMGSRV_BASE/<token>/x.jpg` 能看到图，
   再去群里看预热那条有没有图。

## 为什么不用 MinIO / nginx / 群晖套件

**写入方和读取方是解耦的**：`publish()` 只负责往 `data/imgserve/` 落一个文件 +
返回 URL，HTTP 那半截是**无状态的、可替换的**。所以不该为「一天几张图」引入
一个有状态的服务：

| 方案 | 判据 |
|---|---|
| **同进程 stdlib**（现在这个） | 只读、量小、单一消费者（QQ 的图代理）—— 够 |
| nginx / caddy 挂同一个目录 | 真多人看、要 Range / keep-alive / 限速时再上，**URL 形态不变**，代码不用改 |
| MinIO（S3） | 要有 S3 客户端才划算，我们没有 |
| Filebrowser / Chevereto | 方向不对：那是给人上传、看相册用的 |
| 群晖 Web Station | 暴露真实目录、没有随机路径和 TTL，还只能用 80/443（电信封） |

以后要换成 nginx，就是把 `bot.py` 里那几行换成一个容器 + 挂
`./data/imgserve:ro`，`/<token>/<file>` 一个字不用动。

## ⚠️ 访问日志是这套方案最值钱的东西

「群里没图」的时候，**第一个要回答的问题是 QQ 到底有没有来抓**：

- 有 `imgsrv <QQ 的 IP> /<token前8位>…/<file> 200 N` → 抓了，问题在渲染 /
  尺寸 / QQ 侧的缓存策略；
- **没有这一行** → 它根本没找到我们（路由器转发、DDNS、或 QQ 拒绝访问）。

所以每次请求都记 **INFO**（`log_request`），路径只打 token 前 8 位 ——
完整 token 是那张图的钥匙，没必要进日志。走 nginx 就只能去翻它的 access.log。

⚠️ **日志里的来源 IP 永远是 `172.26.0.1`（Docker 的网桥网关），不是真实客户端。**
原因是端口由 Docker 的 userland proxy 转发，源地址在那一层就被改写。所以
「有没有人来抓」能看出来，**「是不是 QQ 来抓的」看不出来** —— 分辨只能靠时间
（我们自己测的时间是已知的）。想拿真实 IP 得关 `userland-proxy`（要 root 改
dockerd 配置并重启 Docker），代价比收益大，不做。

## 以后要做「批量图库」的话

1. **按内容哈希命名**（sha256）天然去重，顺手能回答「这张是不是已经有了」。
2. **单独一张 SQLite 索引表**记「谁 / 什么时候 / 来源 URL / 属于哪个功能」——
   文件系统不擅长回答这种问题。
3. **前缀区分生命周期**：`cleanup()` 只删 `[0-9a-f]{32}` 这类目录，
   永久库用别的前缀（比如 `perm-…/`）就永远不会被清。这是特意留的。
4. **家宽上行是真瓶颈**：6 张 1.5 MB = 让 QQ 从家里拉 9 MB。偶尔一次无所谓。

## 实测：预热不需要（2026-10-22 推翻的旧结论）

「QQ 的图片缓存冷链接第一次必炸」这条**是在 `pbs.twimg.com` 上得到的**（1.6 MB 不炸
/ 3.4 MB 全炸）。换成自建图床后复现不出来：

| 实测 | 结果 |
|---|---|
| 3.5 MB、从未被访问过的图，**不预热**直接发 | 群里正常显示，图床日志一条 200 |
| 一条 markdown 塞 12 张图 | 12 张全部渲染（含 3 张 4.5 MB） |
| markdown 正文 8000 字 | 完整显示 |

所以**别再按「必须预热」设计新功能**。真遇到图不显示时，先看图床访问日志：

- **有 200 记录** → QQ 抓到了，问题在渲染（尺寸提示、比例、缓存）；
- **没有记录** → 它根本没找过来（路由器转发、DDNS、URL 打错）。
