# 图库与图床

2026-10-22 加。**两个角色，别混**（`GLOSSARY.md` 里也有）：

| | 代码 | 职责 |
|---|---|---|
| **图库** | `imagelib.py` | 存图、去重、按 角色/日期/来源 查回来。**不自动过期** |
| **图床** | `imgsrv.py` | 把图库里已有的图通过 HTTP 发出去，只读 |

图床回答「这张图现在能不能被 QQ 抓到」，图库回答「我们以前收过哪些图」。

## 为什么非要有它

生日贺图是**一个偶像一条 markdown**，正文里 `![](url)` 放最多 6 张图。
2026-10-22 真发了两遍，**预热 45 秒和 180 秒，群里都一张图没有**。

根因不是格式、不是尺寸、更不是预热不够：

> **markdown 的图是 QQ 的服务器去下载的。** 它在大陆机房，**够不到
> `pbs.twimg.com`**。

对照实验就在同一个功能旁边：偶像大师 NEWS 那条链路用 `idolmaster-official.jp`
的 CMS 图，`![](url)` **一直显示得好好的**。所以「QQ 抓不到境外图」是错的 ——
它抓得到日本站，**只是抓不到推特**。

结论：图必须**我们自己托管一份**。

## 存储：内容寻址，分类靠索引

```
<库根>/blobs/<sha256 前两位>/<sha256>.<扩展名>
```

文件名就是内容的 sha256。同一张图被贺图和预览各引用一次，**只存一份文件**，
索引里是两行 `image_refs`。为什么不做成「按偶像分文件夹」见
[`adr/0002-content-addressed-library.md`](adr/0002-content-addressed-library.md)。

两张表：`images`（内容本身的属性）+ `image_refs`（每次出现的上下文）。

**元数据在入库那一刻抓** —— 作者会改名、账号会删、点赞会一直涨，事后再也补不了。
所以 `author_name` / `author_category` / `likes_at_capture` 都是**快照**。

日期存两个：`event_date`（业务日期，贺图取**被庆祝的那天**）和 `captured_at`
（真实入库时刻）。分类浏览用前者 —— 只存一个的话，回看某年生贺一定错位一天。

## 寻址

```
http://<IMGSRV_BASE>/i/<sha256>.<扩展名>
```

- 只认 `/i/<64 位小写十六进制>.<白名单扩展名>`，其它一律 404 —— 路径穿越在正则
  这一层就断了。目录列表、根路径、大写哈希、`.exe`、旧式 32 位 token 全部 404。
- **绝不给 URL 加 query 参数** —— QQ 的图片代理碰到多余的参数就抓不到。
- 地址不可变（内容哈希），所以给了长缓存头。
- 扩展名按**魔数**定，不信源站 URL 后缀。
- 单张上限 12 MB，超过的不入库也不服务。

## 网络：家里两条宽带，只有一条有公网 IP

```
有线宽带（公网 IP）→ 路由器(LAN) → NAS 网口 1
另一条宽带（PPPoE，CGNAT）→ NAS 网口 2
```

- 公网 IP 在**路由器后面**那一侧（NAS 的 LAN 2，`192.168.0.6`）。
- PPPoE 那条是 `100.101.80.44`（`100.64/10` = **CGNAT，不是公网**），选它没用。

### ⚠️ DDNS 用 DSM 设置里的那个，但两个坑要记住

| DSM 里的选法 | 它干了什么 |
|---|---|
| 「自动」 | 去外部回显服务问 IP，**请求被全局代理接管** → 写进去的是代理出口（日本/香港） |
| 「局域网 2」 | 直接把网卡地址 `192.168.0.6` 写进 A 记录 |

**这两个是「最近几个月都不可达」的真正原因。**「自动」在**关掉全局代理之后是对的**，
但只要哪天再开回全局代理就又会写错 —— 所以图床突然不可达时，**第一个怀疑对象就是代理**。

`www.jacklin513.top` 和 `jacklin513.synology.me` **都配在 DSM 的 DDNS 里**，
两个都会跟着 IP 变。但「配了」和「真的在更新」是两件事，判据只有一条：

```bash
dig +short www.jacklin513.top     # 和下一行比
curl -s http://ip.3322.net
```

### ⚠️ 最后一公里：路由器必须做端口转发（**只能用户本人做**）

DDNS 只保证「域名 → 正确的公网 IP」。**IP 通不等于端口通** —— 入站还要路由器
转发一条：`WAN 18080 → 192.168.0.6:18080`。

- **别转发 80 / 443**：电信入站封这两个（实测外部探测 80/443 一律超时）。
- NAS 的 LAN 2 建议在路由器上**做静态 IP 绑定**，否则重启后地址一变转发就错。

### 怎么读外部探测的结果

| 现象 | 含义 |
|---|---|
| **`Connection timed out`** | 包被丢了（多半是 ISP 侧拦了，80/443 就长这样） |
| **`Connection refused`** | 有人回 RST —— **路由器上没有这条转发** |
| 正常应答 | 转发通了 |

2026-10-22 那次：NAS 本机明明在听的三个端口，外部**全是 refused** ——
说明路由器一条转发都没有，不是「服务没起」。

## ⚠️ 访问日志是这套方案最值钱的东西

「群里没图」的时候，**第一个要回答的问题是 QQ 到底有没有来抓**：

- 有 `imgsrv … /<哈希前8位>…<扩展名> 200 N` → 抓了，问题在渲染 / 尺寸 / 缓存；
- **没有这一行** → 它根本没找到我们（路由器转发、DDNS、或 URL 打错）。

所以每次请求都记 **INFO**，路径只打哈希前 8 位。

⚠️ **日志里的来源 IP 永远是 Docker 的网桥网关**（`172.x.x.1`），不是真实客户端 ——
端口由 Docker 的 userland proxy 转发，源地址在那一层就被改写。所以「有没有人来抓」
能看出来，**「是不是 QQ 来抓的」看不出来**，只能靠时间推断。

## 实测：预热不需要（2026-10-22 推翻的旧结论）

「QQ 的图片缓存冷链接第一次必炸」这条**是在 `pbs.twimg.com` 上得到的**（1.6 MB
不炸 / 3.4 MB 全炸）。换成自建图床后复现不出来：

| 实测 | 结果 |
|---|---|
| 3.5 MB、从未被访问过的图，**不预热**直接发 | 群里正常显示，图床日志一条 200 |
| 一条 markdown 塞 12 张图 | 12 张全部渲染（含 3 张 4.5 MB） |
| markdown 正文 8000 字 | 完整显示 |

所以**别再按「必须预热」设计新功能**。

## 部署要点

1. `.env`：`IMGSRV_BASE=http://<域名>:18080`（空 = 图床关闭，图照样入库但群里看不到）。
2. `docker-compose.yml` 里 bot 服务发布了 `18080:18080` —— **改了要 `up -d`**，
   `restart` 不会重建容器、端口映射不生效。
3. 路由器：`WAN 18080 → NAS 18080`。
4. 验：手机 4G 打开 `IMGSRV_BASE/i/<任意哈希>.jpg` 应该 404（通了但没这张），
   再发一条带图的推送，看群里有没有图。

## 其它

- 图不放 `data/` 以外的地方，也不进 git（`data/` 本来 gitignore）。
- 版权：贺图是画师的，署名 + 原推链接在文案里。
- 旧版图床用的是 `data/imgserve/<32 位随机 token>/`，**已经不再服务**，可以手工删掉；
  没迁移是特意的（那些 URL 本来就按 7 天过期设计）。
- 图床只服务图库这一件事。**别加路由** —— 那等于给公网开洞。
