# 偶像生日推送（2026-10-19 加）

每天 **23:05**（北京时间）一条：当天过生日的偶像 + 声优名单，配一张 imas_ch
发的合并祝贺图。数据分两半，来源完全不同 —— **这个划分是整套设计的地基**：

| | 来源 | 什么时候取 |
|---|---|---|
| **名单**（谁生日 + 声优和角色） | `data/birthday/birthdays.toml`（冷数据） | 扒一次存着，运行时只读本地文件 |
| **配图** | `https://x.com/imas_ch` 当天那条祝贺推 | 每天实时抓 |

名单是**角色设定，不会变** —— 366 天几百 KB，扒一次存着，少一个「imas-db 挂了
今天就没推送」的依赖。配图是**当天才发的**，只能实时抓。两条链路**互相独立**：
抓不到图只是少一张图，**名单照样发**（窗口末尾退化成纯文字）。

### ⚠️ 23:05 推的是**第二天**的生日（整个功能最容易写错的一行）

用户定的：生日推送的正日子是**日本时间当天 0 点** —— imas_ch 正好在北京时间
**23:00**（= 日本 0 点）发那条推。所以我们 23:05 起跑去抓，于是：

    10-18 晚上 23:05  →  推的是 **10-19** 的生日

`slot_for()` 给推送时刻，`birthday_date()` 把它 **+1 天**，**库里也按被祝福的
那天记**（`2026-10-19`）。写成 `slot.date()` 的话每天的推送会整体**早一天**，
而且从日志上完全看不出来 —— 名单和推文取自同一份数据，只是整体错位。
smoke `[4.96]` 有跨月 / 跨年 / 闰日四条钉子钉这个。

### 推文怎么找：x.com 的**服务端渲染时间线**

    GET https://x.com/imas_ch          （未登录，约 163 KB）

页面里同时有 `data-href="/imas_ch/status/<id>"`、`{"timestamp":<13位毫秒>}`、
正文（`whitespace-pre-wrap ... dir="auto"` 那个 div）和 `pbs.twimg.com/media/<id>`。
一页约 6 条（含置顶），够找当天那条了。

**这是目前唯一免登录能拿到它的路。** 试过的死路（别再试）：
`cdn.syndication.twimg.com/timeline/profile`、`syndication.twitter.com/srv/…`
（都是 000）、`api.twitter.com` guest API（SSL 被墙）、fxtwitter 的
`/timeline` `/media` `/statuses` `/tweets`（全 404）、Nitter 镜像（xcancel 451、
其余 000）、`publish.twitter.com/oembed` 对 profile（301）、第三方抓取站
twstalker / sotwe / twiiit（403）。`api.fxtwitter.com/<screen_name>` **只有资料、
没有时间线**。

三条**必须**记住的解析细节：

- **挑推的判据是「正文里的日期 + `お誕生日おめでとう`」，不是「最新一条」。**
  imas_ch 除了生日推还发配信、周边、会员招募，盲取最新会取错。日期匹配要
  `(?<!\d)M/D(?!\d)` —— 否则 `1/1` 会匹配上 `11/1`。
- **必须按 id 去重。** 一条推被另一条**引用成卡片**时会在页面里出现两次
  （实测撞到过），不去重的话同一条生日推解析两遍、图发两张。
- **图 URL 强制 `?name=orig`**（原图）。和 `preview.py` 那条产品要求一致。

页面结构一变 `parse_timeline` 就返回空表 —— 这时**必须打 WARNING**，
否则症状是「每天都没图」，看着像 imas_ch 没发。

### ⚠️ 容器直连全不通，这条路**必须**走 `MEDIA_PROXY`

2026-10-19 容器内实测：

| 目标 | 直连 | 经 `MEDIA_PROXY` |
|---|---|---|
| `x.com/imas_ch` | ❌ SSL 握手超时（墙） | ✅ 200 / 163 KB |
| `pbs.twimg.com/media/…` | ❌ `Errno 99`（DNS 被污染） | ✅ 200 / 115 KB |
| `imas-db.jp`（扒冷数据用） | ❌ 超时 | ✅ 200 |

**没有证书错误** —— Surge 没 MITM 这两个域名，所以 `MEDIA_CA_BUNDLE` /
`MEDIA_INSECURE_TLS` 在这里都用不上（虽然线上配着）。客户端一律复用
`preview.make_client(cfg.media_proxy, …)`，**别另起一个**；`bot.py` 里传的是
`self.media_http`（`smoke [4.96]` 有一条只看源码的钉子钉这个）——
换成 `rss_http` 之后代码照样跑、日志照样正常，只是每天都没配图。

图片**必须我们自己托管**：不能把 `pbs.twimg.com` 的 URL 交给 QQ 去抓 ——
**QQ 的服务器在国内，同样够不到 Twitter 的图床**（和 `i.ytimg.com` 是同一个问题）。

2026-10-22 起走：`preview.fetch_image` 下载 → **存进图库** → 文案和 `![图1 …]`
拼成**一条 markdown** 发出去。以前是下载后 base64 上传（`send_local_image`，
`msg_type=7`），现在那条路已经删了；顺带摆脱了它 3.5 MB 的原图上限。

### ⚠️ 窗口是**抓图的补发窗口**，和早安那个 180 秒不是一个意思

早安是纯本地文件，`MORNING_WINDOW_SEC` 只覆盖调度抖动。这里要实时抓推文：
imas_ch 23:00 发、我们 23:05 起跑，正常第一拍就有，但它偶尔晚几分钟、
或者网络抖一下。所以 `BIRTHDAY_WINDOW_SEC`（默认 **300** 秒）内**每拍都重试**，
到窗口末尾（`late + CHECK_SEC >= window`）还没抓到就**发纯文字**。

**绝不因为没图就不发** —— 名单从来不依赖推文。

### 名单**不做任何过滤**

961プロ（反派）、Xenoglossia（机甲 AU）、その他 全都发。用户明确要求
「能从 imasdb 抓下来的都要显示」。品牌表（`[brands]`）只是给排查用的，
渲染时一行标签都不加。

文案的**顺序是偶像在前、声优在后**，声优带 `(角色役)`；没有角色的不硬拼括号：

    🎂 2026/10/19 本日のお誕生日:
    杜野凛世
    榎木淳弥 (舞田類役)
    大塚剛央 (眉見鋭心役)
    土屋翔 (舞台SideM 伊瀬谷四季役)

文件名里的角色本身就是这个形态（`舞台SideM 伊瀬谷四季`），**不要再去拆**。

### 其他

- **`data/birthday/` 是冷数据，一次性扒**：`scripts/fetch_birthday_source.py`
  （扒 `https://imas-db.jp/calendar/birthdays.html`，**要挂代理**，
  本地跑不了就在 NAS 上跑）。产出 `birthdays.toml`，366 天 / 382 位偶像 /
  313 位声优 / 12 个品牌 / 46 天没人过生日。`data/` 不进 git，**同步到 NAS
  时手动传这一个文件**。
- ⚠️ **没人过生日的那天根本没有 `idols` / `people` 键**（不是空数组）。
  读取端必须 `.get(k, [])`，写成 `entry["idols"]` 会在那 46 天 KeyError。
- ⚠️ **不需要判闰年**：`datetime.date` 本身构造不出平年的 02-29，所以
  `"02-29"` 这个键只在闰年会被查到。别加 `isleap` 分支 —— 那是走不到的死代码。
- **冷数据读不到只打 ERROR 并关掉功能，不抛。** 它是锦上添花的功能，不该让
  整个机器人起不来（`data/birthday/` 是 gitignore 的，全新部署本来就没有
  这个文件）。但**一定要能看见** —— 每天少一条推送，从群里是看不出来的。
- **落库的键是「被祝福的那天」+ 群**（`birthday_posts`），不是推送时刻。
  按推送时刻记的话「10-18 晚上推的 10-19 生日」和「10-19 晚上推的 10-19 生日」
  会分成两行，而它们本来就是同一天，重试 / 重启时会重复发。
  `tweet` 字段**空串 = 当时没抓到图**，不是漏填 —— 排查时能分清
  「当时没图」和「当时压根没记」。
- **多群发同一份文案和同一张图**（选人 / 抓图都在循环外）。
- `scripts/probe_birthday.py` 离线看（**默认不发消息、一次网都不上**）：
  冷数据统计、slot / 被祝福的那天 / 窗口判定、渲染出来的原文、库里发过哪些群。
  `--fetch` 才真去抓一次推文，`--send <openid>` 才真发 —— **`--group` 故意
  没有默认值**（群 openid 不是群号，看不出是不是测试群）。`--send` 走的是
  **真实轮询器**（套一个裸 HTTP 的假 sender，不抢线上实例的 WebSocket 会话），
  并把窗口临时收成「刚好用完」好让它立刻发。
