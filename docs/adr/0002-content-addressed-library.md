# 图库按内容寻址存，分类靠索引而不是目录

图库要回答的问题是「我们收过哪些图、按角色 / 日期 / 来源怎么找回来」，而不是
「这张图放在哪个文件夹」。**分类本质是一次查询**：一张贺图同时属于某个角色、
某一天、某个作者，放进目录结构只能选一个维度，其余维度就得靠命名约定，久了必乱。

所以物理层用**内容寻址**（文件名 = 内容的 sha256，按前两位分桶），逻辑层用
SQLite 索引表。同一张图被贺图和链接预览各引用一次只存一份；改分类不用搬文件；
哪天要「能翻文件夹」，再从索引生成一棵硬链接视图树即可 —— 因为 `blobs/` 里的
文件**永不改写**，视图是纯派生品。

## 考虑过的选项

- **按分类存目录**（`<角色>/<日期>/<推文id>.jpg`）：人眼能直接翻，但去重靠猜、
  加一个新分类维度就要把所有文件搬一遍，**不可逆**。相册软件（PhotoPrism、
  Immich）也都不用这种方式呈现「相册」——它们呈现的是查询结果。
- **随机 token 目录**（图床现在的做法）：不可猜，但对图库没有意义 ——
  sha256 本身同样不可猜，还顺带解决了去重和寻址两件事。
- **一张表塞下所有字段**：简单，但「同一张图在不同上下文出现过几次」恰恰是最难
  事后补的信息，而 `images` / `image_refs` 两张表天然回答得了。

## 后果

- 对外 URL 变成 `<base>/i/<sha256>.<扩展名>`，旧随机 token 的 URL 作废
  （已发出的消息里那些图本来就按 7 天过期设计，不迁移）。
- 每次入库都要算一次 sha256 并读一次宽高 —— 两者都是入库时手上就有的数据，
  不增加任何网络请求。
- 「按角色 / 日期翻」需要写一次查询，不能靠 `ls`。要人眼翻的时候另做视图层。
