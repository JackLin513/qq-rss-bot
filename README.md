# qq-rss-bot

QQ 群 RSS 订阅机器人：群里 `@机器人 /sub <RSSHub路由>`，之后有新文章自动推到群里。

## 技术栈与选型理由

| 部分 | 选择 | 为什么 |
|---|---|---|
| 机器人框架 | **qq-botpy（官方 Python SDK）** | QQ 官方机器人没有通用协议，只能走官方 API。Python SDK 是官方维护里最省事的：WebSocket 长连接本地就能跑，不需要公网 IP 和内网穿透 |
| RSS 解析 | **feedparser** | 纯 Python，RSS 0.9x/1.0/2.0/Atom 全兼容，且对畸形 XML 极其宽容（真实世界的源大多不干净） |
| HTTP | **httpx** | 异步，方便和 botpy 共用一个事件循环；超时/重定向控制清晰 |
| 存储 | **SQLite（标准库）** | 单文件、零运维、单机机器人够用。去重表增长有上限，见 `prune_seen` |
| 调度 | **自己写的 asyncio 轮询** | 每 30s 查一次「哪些订阅到点了」。不引 APScheduler 是因为间隔状态在数据库里，重启不需要重建任务，比 cron 式调度更好恢复 |
| 依赖管理 | **uv** | `uv sync` 一把梭，锁定版本 |

**为什么不用 Node/Java/Go**：这三个官方也有 SDK，协议完全一样。但这个项目 80% 的复杂度在 RSS 解析的脏数据容错上，feedparser 在这个环节的优势很明显；而 botpy 已经把 WebSocket 重连、鉴权、心跳全处理好了，换语言省不下东西。

## 快速开始

```bash
uv sync
cp .env.example .env      # 填入 AppID / AppSecret
scripts/botctl.sh start   # 后台启动，日志在 /tmp/qq-rss-bot.log
```

`scripts/botctl.sh` 还有 `stop` / `restart` / `status` / `log -f`。
**改完代码要 `restart`** —— Python 没有热加载，不重启就还是旧代码在跑
（这个坑踩过一次：`/new` 报了「未知指令」，其实是进程比改动早起了 16 分钟）。
前台调试直接用 `uv run qq-rss-bot`。

### 1. 部署 RSSHub（必做）

**官方公共实例 `rsshub.app` 现在对本项目返回 HTTP 403，直接用不了**（2026-10 实测）。自建：

```bash
docker run -d --name rsshub -p 1200:1200 diygod/rsshub
```

`.env` 里填 `RSSHUB_BASE=http://127.0.0.1:1200`。
想临时验证可以先用镜像 `https://rsshub.rssforever.com`（实测可用，但公共实例随时可能挂）。

### RSSHub 路由可用性（实测）

自建 RSSHub 默认只带「不需要额外配置」的路由。实测结果：

| 路由 | 结果 |
|---|---|
| `/hackernews/best`、`/v2ex/topics/hot`、`/sspai/index`、`/solidot/linux`、`/36kr/newsflashes`、`/ithome/it`、`/readhub/daily`、`/douban/movie/playing`、`/juejin/category/frontend`、`/infoq/recommend` | ✅ 开箱可用 |
| `/github/trending/*` 等 GitHub 路由 | ❌ 503 `ConfigNotFoundError` —— 需要给容器加 `GITHUB_ACCESS_TOKEN` |
| `/weibo/user/*`、`/bilibili/hot-search` 等 | ❌ 503 —— 需要浏览器，换成 `diygod/rsshub:chromium-bundled` 镜像 |
| `/zhihu/hotlist` | ❌ 404 —— 路由已被上游删除，换别的知乎路由 |

加 GitHub token 的做法：

```bash
docker rm -f rsshub
docker run -d --name rsshub --restart unless-stopped -p 1200:1200 \
  -e GITHUB_ACCESS_TOKEN=ghp_xxx diygod/rsshub
```

用 `uv run python scripts/check_sources.py` 可以随时复测路由可用性。

### 2. 开放平台配置（q.qq.com → 你的机器人）

- **开发设置** → 复制 `AppID` / `AppSecret` 到 `.env`
- **事件订阅** → 勾选**群聊@机器人消息**（群聊管理类事件可选，用于记录群）
- **沙箱配置** → 填测试群，未上架的机器人只在这些群生效
- **权限** → 开启**「机器人主动在群聊内发言」**。不开的话只能被动回复，定时推送会全部失败

### 3. 验证

```bash
uv run python scripts/smoke.py        # 302 项：解析/去重/调度/配图/指令/限流/真实抓取
uv run python scripts/integration.py  # 15 项：端到端（真抓源，假推送，不碰 QQ）
```

## 运行平台

同一套代码支持两种跑法，**差异只在部署形态，代码不用改**（`RSSHUB_BASE` 已是环境变量）。

| | macOS（开发调试） | 群晖 Synology x86_64（长期运行） |
|---|---|---|
| 机器人 | 宿主原生 `uv run qq-rss-bot` | 容器（compose） |
| RSSHub | Docker Desktop | 容器（compose） |
| `RSSHUB_BASE` | `http://127.0.0.1:1200` | `http://rsshub:1200` ← 服务名 |
| 出网代理 | 跟随系统代理 | 需显式配置，见下 |

架构要求 **x86_64**（`diygod/rsshub` 的 amd64 镜像原生运行，无需模拟）。
任何 x86_64 Linux 主机同理，不只群晖。

**为什么地址要改**：容器里的 `127.0.0.1` 是容器自己，不是宿主机。两个服务都进容器后，
bot 必须用 Docker 服务名访问 RSSHub。忘了改的症状是抓取全部超时。

**代理默认只给 RSSHub**：部分上游（实测 `www.v2ex.com`、`github.com`）
国内直连不通——v2ex 的 DNS 被污染，解析到 Facebook 的 IP 段——需要走代理。
但只有 RSSHub 需要；国内站走代理实测没有延迟代价，所以可以全局走。

```yaml
  rsshub:
    environment:
      - HTTP_PROXY=http://<你的代理地址>:6152
      - HTTPS_PROXY=http://<你的代理地址>:6152
      - NO_PROXY=localhost,127.0.0.1
  bot:
    environment:
      - RSSHUB_BASE=http://rsshub:1200
      - HTTP_PROXY=          # 显式清空，防止容器级代理被继承进来
      - HTTPS_PROXY=
      - NO_PROXY=localhost,127.0.0.1,rsshub,api.sgroup.qq.com,bots.qq.com
      - MEDIA_PROXY=http://<你的代理地址>:6152   # 只给 YouTube / X 用
```

**bot 的默认出口不能整体走代理**：`http://rsshub:1200` 是容器内部的服务名，
代理解析不了；而 bot 的命脉 `api.sgroup.qq.com` 是国内站，直连更快更稳。

唯一的例外是 **`MEDIA_PROXY`**——它只作用于 YouTube / X 那**一个**客户端
（`preview.make_client` 建的 `media_http`），因为那两个站点直连完全不通。
两个客户端是分开的，配了它不影响 RSSHub 和 QQ。

详细评估（目标机实机规格、内存账、容器网络实测、四个迁移坑）见
[`docs/synology-migration.md`](docs/synology-migration.md)。

## 指令

| 指令 | 权限 | 说明 |
|---|---|---|
| `/rss` | 所有人 | **按钮菜单**：订阅/退订/列表/搜索都能点 |
| `/sub <路由或URL> [间隔分钟] [--ai]` | 群主/管理员 | 订阅，默认 15 分钟。RSSHub 路由可省略域名，如 `/36kr/newsflashes`。加 `--ai` 同时打开 AI 摘要 |
| `/unsub <编号>` | 群主/管理员 | 取消订阅 |
| `/list` | 所有人 | 本群订阅列表 |
| `/find <关键词>` | 所有人 | 搜 RSSHub 路由，不用记路径 |
| `/new [编号\|all] [条数]` | 所有人 | 读最新几条，默认每源 3 条。**读过的不会再被定时推送重发** |
| `/check <编号>` | 所有人 | 抓一次看源还活着没。**只看，不动推送状态** |
| `/pause <编号>` | 群主/管理员 | 暂停订阅，暂停期间不抓取也不推送 |
| `/resume <编号>` | 群主/管理员 | 恢复暂停的订阅（失败计数一并清零） |
| `/interval <编号> <分钟>` | 群主/管理员 | 改抓取间隔，**不用退订重订**（重订会重建 baseline 丢增量） |
| `/ai <编号> on\|off` | 群主/管理员 | 给某个源开/关 AI 摘要（抓正文 + 翻译/精简）。不带参数列状态 |
| `/ping` | 所有人 | 存活检测 + 统计 |
| `/help` | 所有人 | 帮助 |

**编号是「本群内的位置」，不是数据库 id。** `/list` 永远显示 1、2、3…，
删掉一条后面的自动补位，新群第一条就是 1。
（曾经直接打数据库主键 —— 那是全局自增、跨群共享的，
会让一个从没订阅过的新群把第一条订阅显示成「5.」，删一条还留下空号。）
编号会随订阅增删而变化，所以 `/unsub` 的回复里会带上被删掉那个源的名字，
万一列表在你 `/list` 之后变过，一眼就能看出删错没有。

**订阅是按群共享的。** `subscriptions` 表以 `group_openid` 为作用域：群里任何人订阅，
全群都会收到推送；群与群之间完全隔离。QQ 官方群机器人**不支持**把主动消息定向给
某个成员，所以「全群共同接收」是平台约束，不是实现选择。

**别名与容错**：`help`/`帮助`/`?`、`sub`/`subscribe`/`订阅`、`unsub`/`取消`、`list`/`列表`；
斜杠可省略（`@机器人 sub /x` 也认）；只 @ 不写字直接回帮助；未知指令仅在以 `/` 开头时才回
（避免群里闲聊被插嘴）。

**权限**：`/sub` 与 `/unsub` 默认仅群主和管理员可用，角色取自报文里的
`author.member_role`（botpy 会丢弃它，由 `compat.py` 的补丁补回）。
想放开就设 `RESTRICT_ADMIN_COMMANDS=false`。角色取不到时会**放行并记警告**——
宁可漏管，也不能让机器人整个不可用。

### 找路由：`/find`

RSSHub 有 **4000+ 条路由**，指望用户记住 `/36kr/newsflashes` 这种路径不现实。
`/find` 按站点名、路由名、路径或分类检索，直接给可订阅的路径：

```
「动漫」找到 139 条，显示前 5：
1. ✅ 幻之羁绊动漫网｜资讯
   /005/zx
2. ✅ 78 动漫｜分类
   /78dm/news
...
还有 134 条，换个更具体的关键词。
用 /sub <路径> 订阅。
```

**每条结果都标了在本实例上跑不跑得起来** —— 这是它比翻文档强的地方。
RSSHub 的路由表里带 `features`，能直接判断：

| 标记 | 含义 | 实测条数 |
|---|---|---|
| ✅ | 开箱可用 | 3410 |
| ⚠️ 需要配置 XXX | 缺环境变量，会 503 | 130 |
| ⚠️ 有反爬 | 可能要 cookie 或代理 | 283 |
| ❌ 需要浏览器 | 得换 `chromium-bundled` 镜像 | 181 |

搜索时**可用的排前面**：搜出来却跑不起来是最没用的结果。

数据来自 RSSHub 自带的 `GET /api/namespace`（本地实测 4MB / 2064 站点 /
4004 条路由，一次 0.12s）。结果按天缓存在 `data/rsshub-routes.json`
（精简后 670KB，命中缓存 0.01s）；RSSHub 挂掉时用过期缓存兜底，
不会因为抓不到路由表就整个功能不可用。

**没把描述纳入检索**：实测能让「新闻」的命中从 196 涨到 371 条，
但**前 5 条结果一条都没变** —— 纯体积负担，所以只索引名称/路径/分类。

### 按需读最新：`/new`

定时推送是「有新条目就发」，`/new` 是「我现在就要看最新几条」。
两者共用同一套推送出口和同一条文案，所以群里观感一致。

```
你：@机器人 /new 2 5
机器人：最新 5 条：アイドルマスター 5
        接着逐条发 5 条，有图的带图
```

| 写法 | 含义 |
|---|---|
| `/new` | 全部订阅，每个源 3 条 |
| `/new 2` | 第 2 个订阅，3 条 |
| `/new 2 5` | 第 2 个订阅，5 条 |
| `/new all 5` | 全部订阅，每个源 5 条 |

**读过的条目会被标记为已见**，定时推送不会再原样重发一遍 ——
否则你主动看一眼，过几分钟机器人又把同样的东西刷一次。
标记只给**真发出去**的条目：发送失败或被上限截掉的留给定时推送补发，
语义和推送本身一样是 at-least-once。

上限是为了避频控（群维度 20 qpm，而这里每条都可能带一张图）：
单源最多 10 条、单次最多 15 条，超了会在回执里说明省略了多少。
回执本身走**被动回复**，不占主动消息额度。

### 按钮菜单：`/rss`

`/rss` 回一条带按钮的卡片，订阅管理都在按钮里。退订按钮是**按本群实际订阅现算的**，
点一下就把完整指令 `/unsub 1` 填进输入框，不用回去数编号：

```
📋 本群订阅（1）
1. 偶像大师 / 15min

[订阅列表] [搜索源]
[订阅源]   [改间隔]
[退订 1]              ← 点了直接插 /unsub 1
[暂停]     [恢复]
```

超过 4 个订阅时退订那行折叠成一个「退订…」，点开是第二张卡片，把全部订阅平铺出来。

两个要注意的地方（都是这个平台「接口返回 200 不等于生效」的老毛病）：

- **按钮的 `label` 上限是 10 显示宽度（中文按 2），比指令面板的 14 还紧。**
  「退订 偶像大师」宽 13，直接超限。所以 label 里只放编号，名字放在卡片正文里 ——
  正文就在按钮上方，不会看不懂。
- **按钮点下去只是把文字填进输入框，不会自动发送**，还得自己按一下发送。

`/rss` 走的是**被动回复**，不占主动消息配额（配额都留给推送）。

### 进群自动订阅

用 `AUTO_SUBSCRIBE_FEED` 配一个默认源（RSSHub 路由或完整 URL），机器人被拉进新群时
自动订上，省得每个群都去敲一遍 `/sub`：

```bash
AUTO_SUBSCRIBE_FEED=/idolmaster/news
```

留空 = 关掉这个功能。

启动时还会**给所有已知的群都补上**（不只是零订阅的）。有订阅的群也补：要么
已经订了这个源（幂等，白补），要么订的是别的源、正好缺这一个。已知副作用是
**某个群故意退订了这个源，下次启动会被补回来**。

**但机器人只认识它「见过」的群。** 新部署的空库一个群都不认识，启动日志会写
「本次给 0 个群补上了」——这时在群里 @ 一次机器人（让平台把 group_openid 报过来），
之后重启就会自动订上。也可以直接 `/sub`，一步到位。

两个细节：

- 补订阅**只写数据库，不立刻抓源**。抓一次最长要 20 秒，在事件回调里干等会把
  消息分发卡住。轮询器下一拍（≤30 秒）才建立基线并抓取，所以 `/list` 里一开始
  显示的是路由串，半分钟后变成真实源名。
- 进群欢迎语走**主动消息**（进群事件本身没有可回复的消息 id），**需要该群已经打开
  「机器人主动在群聊内发言」**。没开的话那条欢迎语会静默失败，但订阅本身已经生效。

### 群里分享 bilibili 链接

群里**任何人**发 bilibili 链接（不需要 @ 机器人），机器人自动回一张带封面、
标题、UP 主和播放数据的卡片：

```
![封面](https://i1.hdslb.com/...@480w_270h_1c.jpg)
**【中字熟肉】气象厅の狠活！…**
中气爱mini · 03:07
播放 3.1万 · 弹幕 62
评论 336 · 点赞 1056
[在 bilibili 打开](https://www.bilibili.com/video/BV15eJt6pEam)
```

用的是**被动回复**，不占主动消息配额。开关：

```bash
BILIBILI_PREVIEW=true     # false 关掉
```

**四种分享形态都能认**（都是群里实测抓到的真实报文）：

| 分享方式 | 视频 ID 从哪来 |
|---|---|
| 纯文本里带 `https://b23.tv/xxx` | 跟一次 302 拿到 BV 号 |
| 纯文本里带 `BV` 号 / `av` 号 | 直接用 |
| 图文 H5 卡片 | 卡片文本里的 `jump_url` |
| **QQ 小程序卡片** | 报文里**没有**视频 ID，拿卡片标题去 bilibili 搜索反查 |

最后一种靠「标题去掉标点后**恰好一条**匹配」才认，匹配不上或匹配到多条都
**静默不回** —— 宁可不回，也不能回错视频。

**解析不出来时群里什么都不发**，不会因为认不出链接就回一句报错 —— 但
**日志里记全**（认出了却没解析出来是 WARNING），否则线上「发了没反应」
根本没法查。启动时还会自检一次并写进日志：

```
bilibili 预览连通性自检：✅ 正常（BV15eJt6pEam 【中字熟肉】气象厅の狠活！…）
YouTube / X 预览走代理 http://192.168.0.63:6152
YouTube / X 预览连通性自检：YouTube ✅ Rick Astley - Never ；X ✅ "No one is born hati
```

看到 ❌ 就是容器出网有问题（DNS / 代理 / 证书），不用再往下查了。

几个已知行为：

- **不做去重**：同一条视频发两遍就回两遍。一条消息里含多个链接时只回第一个。
- **数据固定两项一行。** 四项挤一行在手机窄屏上会由 QQ 自己折行，折点不受控
  （实测「播放…弹幕…评论…点赞」会在中间断开）。固定 2+2 是确定的排版，
  宽屏上也不难读。
- 封面走 bilibili 图床的缩略图（原图 214KB → 33KB），由 QQ 平台自己下载转存。
- 想先看看渲染效果再决定发不发，用 `scripts/probe_bilibili.py`（默认只打印，
  加 `--send <group_openid>` 才真发）。

### 群里分享 YouTube / X(Twitter) 链接

同样的机制：群里任何人发一条 YouTube 或 X 链接，机器人自动回一条
（带封面的那种）。

```
Rick Astley - Never Gonna Give You Up (Official Video) (4K Remaster)
Rick Astley
03:33 · 播放 18.3亿
https://www.youtube.com/watch?v=dQw4w9WgXcQ
```

```bash
YOUTUBE_PREVIEW=true
TWITTER_PREVIEW=true
PREVIEW_MULTI_IMAGE=true   # 推文多图 → 连发多条（不占主动配额）
RSS_MULTI_IMAGE=true       # 一条资讯多图 → 发多张（几张看下面那个开关）
MULTI_IMAGE_MARKDOWN=true  # 多图合并成一条 markdown（关掉 → 连发，每张各占一条配额）
PUSH_SUMMARY=true          # 推送文案带 RSS 摘要（关掉退回三行）
MEDIA_PROXY=http://192.168.0.63:6152   # 必填，见下
```

#### 为什么非得自己下载图片

**这两个站点的图，QQ 的服务器拉不到。** 实测（同一时刻、同一个群、同一个接口）：

| 图床 | 交给 QQ 去下载 | 结果 |
|---|---|---|
| `i1.hdslb.com` | ✅ | 拿到 `file_info` |
| `i.ytimg.com` | ❌ | `850027 富媒体文件上传超时`（err_code 40034003）|

`40034003` 是**超时**，不是 404 也不是 DNS 失败——QQ 的机房够得到域名、拉不下
内容。所以「能不能给 QQ 一个 URL 让它自己下」取决于 **QQ 机房到那个图床的
连通性，我们控制不了**。这两个站点因此换了一条路：

    我们自己下载（走代理）→ base64 → 交给 QQ 的 /files 接口

这条路同样实测过（32771 字节的图 → 43696 字节 base64 → 上传成功拿到
`file_info`）。代价是**我们这边必须能出网**，所以 `MEDIA_PROXY` 是必填项——
容器直连这两个站点全部超时。

#### 为什么发的是「富媒体消息」而不是 bilibili 那种卡片

QQ 的 markdown 语法里的 `![](url)`，图片**同样是 QQ 的服务器自己去下载的**，
所以它带不了这两个站点的图。富媒体消息（`msg_type=7`）的图是我们上传的字节，
不经过 QQ 的下载环节。所以：**有封面走富媒体，没封面才退回 markdown 卡片**。

#### 一条消息只能带一张图

网上流传「一条消息可以有 5 个以内的富文本」——**官方文档里没有这条**。
`MediaInfo` 只有一个 `file_info` 字段，所以 `msg_type=7` 一条消息 = 一个媒体文件。
真要一次发多张，只能递增 `msg_seq` 连发多条被动回复（文档明确支持，代价是刷屏），
或者退回 markdown 的多个 `![](url)`（图片又得 QQ 自己去下载，不可靠）。

#### 多图：连发多条，不是一个开关管全部

一条消息塞不下两张（`MediaInfo` 只有一个 `file_info`），所以推文预览的多图是
**连发多条**：第一条带正文和首图，后面每条一张图，最多 4 张。

**RSS 推送不一样**：多图默认**合并成一条 markdown**（`MULTI_IMAGE_MARKDOWN=true`），
正文、最多 6 张图、原文链接全在一条里 —— 一条带 6 张图的资讯也是 1 条消息。
图片要在消息里渲染，尺寸提示是必填的，所以每张图会先读一次真实宽高；读不到的、
以及 QQ 抓不到的那几张会被剔掉并私聊告警。这条路任何一步没走通，都会**自动退回
连发**，一条图都不会少。

三个开关**分开控制**，因为代价差一个量级：

| 开关 | 默认 | 管哪条路 | 代价 |
|---|---|---|---|
| `PREVIEW_MULTI_IMAGE` | `true` | 群里分享的 YouTube / X | 被动回复，**不占主动配额** |
| `RSS_MULTI_IMAGE` | `true` | 定时推送 + `/new` | 主动消息，**每张图各占一条配额** |
| `MULTI_IMAGE_MARKDOWN` | `true` | 上面这条的**形态** | 合并成 1 条 markdown；关掉退回连发 |

后面几条图的文案是「（图 2/4）」这种占位 —— 一条 `msg_type=7` 只能带一个媒体，
正文和首图已经用掉了那一条，所以多出来的图只能各带一句短文案。

RSS 那条在关掉 `MULTI_IMAGE_MARKDOWN` 时，一条带 4 张图的资讯就是 4 条配额
（群维度 20 条/分钟 + 每日上限）。觉得刷屏就关掉对应的那个 ——
**只关 RSS 那条**是常见的选择，预览那条不占配额。

连发中间某张被 QQ 用 `500 消息发送异常，请稍后重试` 拒掉时（实测遇到过），
会自动隔 1 秒重试一次；重试仍失败就跳过那一张，**不会把整条拖回去重发**。
第一条（带正文那条）实在发不出去才会退回纯文字卡片。

#### 正式群推送前的预热 + 人工预览

**QQ 的图片缓存是服务端、跨群共享的，但冷链接第一次渲染必炸。** 实测：一批
3.4 MB 的图 6 张**全裂**；同一批**一模一样的 URL** 隔 20 秒发到**另一个群**，
6 张**全好**。冷发那次一张都没抓下来（客户端上什么都没缓存），所以问题在 QQ
服务端，不在你的手机。**图越大越容易触发**（1.6 MB 不炸、3.4 MB 全炸）。

所以正式群之前分三段**串行**发（并发发下去预热就白做了）：

```
预热群 → 等 45 秒 → 预览群 → 等 30 秒 → 正式群（其余全部）
```

```bash
WARMUP_GROUP=<group_openid>    # 留空 = 关闭整个机制，行为完全退回原来的
PREVIEW_GROUP=<group_openid>   # 同时是给你看的预览群
PREVIEW_WARMUP_SEC=45          # 图大要调大（5 MB 以上给 60+）
PREVIEW_VETO_SEC=30            # 这段时间正式群一条都不发
```

* **预热群那条的图会是裂的**，这是正常的 —— 它唯一的作用就是把 QQ 服务端的缓存喂热。
* **预览群那条是给你看的**：不想发就在群里 **@机器人 说「不发」**，这一条就不进正式群。
  过了窗口没喊停就正常发。喊停**只在窗口内有效**，窗口外随口一句不会误伤下一条。
* 填的是 **group_openid，不是群号**（把机器人拉进群，日志里的「已记录新群」就是）。
* **一个预热群够所有正式群用**（缓存是全局的）。

代价：每条资讯多 1 条主动消息（走预热群自己的额度，不动正式群），
**推送会晚约 1 分钟到达**。

#### 大图的上限是 3.5MB，不是 5MB

`file_data` 官方限 5M，而**限的是 base64 之后那一串**，不是原始字节。base64
膨胀 4/3，所以原始图最多约 3.75MiB，代码里取 3.5MB（`preview.MAX_IMAGE_BYTES`）。
超过这个尺寸会**只发文字不发图** —— 推文的图我们坚持要原图，但图大到传不上去时，
卡片本身不会跟着丢。

取数也分了两条路（详见 `src/qq_rss_bot/preview.py` 顶部）：

| | 主 | 兜底 |
|---|---|---|
| YouTube | `youtubei/player`——有时长和播放量 | oEmbed——**没有这两项** |
| X | fxtwitter——正文/互动数/配图一次给全 | 官方 oEmbed——**没有图，也没有互动数** |

X 之所以用第三方 fxtwitter：官方 oEmbed 只给作者名和正文（正文还藏在 html 的
blockquote 里），官方 syndication 实测本机直接连不上。

几个已知行为：

- **不做去重**：同一条链接发两遍就回两遍；一条消息里含多个链接只回第一个。
- 封面**下载失败或上传失败都会降级成不带图的卡片**，文字一条不少。
- 推文配图取 `name=small`（原图动辄 2MB，base64 之后更大）。
- 想单独验证这条链路（不碰 QQ、不发消息）：
  ```bash
  sudo docker compose exec bot python scripts/probe_meta.py --proxy http://<代理>:6152
  ```

### 主动消息的限流与配额

官方频控是**群维度 20 条/分钟、每群每天 1000 条**，而推送是逐条发的
（一条图文消息只能带一张图），很容易撞上。所以有两层保护：

| 层 | 机制 | 超了会怎样 |
|---|---|---|
| 每分钟 | 令牌桶（容量 = 速率 = 20） | **排队等**，消息一条不丢，只是慢一点 |
| 每天 | 落库计数（默认上限 900） | **拒发**，并私聊告诉管理员 |

用令牌桶而不是「每条 sleep N 秒」，是因为官方是滑动窗口限流：桶允许一次
突发用满 20 条，之后按 20/分钟匀速回填 —— 一次推 25 条不会丢消息，
只是最后 5 条各等 3 秒。

**为什么必须在发送出口做，而不是在每个源的循环里**：轮询器用信号量并发跑
最多 5 个源的抓取循环，每个循环内部逐条 sleep 的间隔是**各自**的，
5 个循环同时跑就等于间隔除以 5。实测 5 个源同时有新内容时，
25 条消息全部落在 **1.6 秒**内。现在整个群维度的发送串行化了，
顺带也保证了消息的到达顺序。

配额**落库**而不是放内存：进程一重启就清零的话，一天的真实用量会被反复低估。
按**本地日期**算，因为 QQ 在本地零点重置。

配额用尽时，**没发出去的条目也会被标记为已见** —— 不标的话，第二天配额恢复
会倒灌一整天的积压。这是有意丢弃，和「一次最多推 5 条」溢出时同样处理。

### 出错通知：只私聊，不在群里报

群里报错对其他人是噪音，还要占主动消息配额。所以这几类事件全部走私聊
（C2C），**群里一条都不发**：

| 事件 | 触发条件 |
|---|---|
| 订阅连续失败被暂停 | 连续 5 次抓取失败（`MAX_FAIL_BEFORE_PAUSE`） |
| 全部源同时失败 | 一整轮里**所有**订阅都抓取失败 → 多半是 RSSHub 或网络挂了 |
| 每日配额用尽 | 当天主动消息发满 |
| **配图发送失败** | 图没发出去（已重试一次）或首图就挂、整条退回纯文字 |

#### 收件人：默认自动登记，推荐改成白名单

**推荐 —— 在 `.env` 里写死收件人**：

```bash
NOTIFY_OPENIDS=<你的openid>
```

填了就是**白名单模式**：只发给名单上的人，数据库里登记的谁都不看。
换群主、加管理员、撤管理员，收件人都不变 —— 这是「只发给我」唯一可靠的做法。

不填则退回**自动登记模式**：收件人 = 在该群发过指令的**群主 + 管理员**
（最多 3 人）。普通成员不会被登记、收不到私聊；但**其他管理员会收到**，
所以默认行为**不是**「只有你」。写死 openid 就把收件人钉死成一个人，
换群主、加撤管理员都不影响。

**openid 不是 QQ 号**，是平台给的「用户 × 机器人」维度的匿名 ID：

- 对**同一个 AppID** 稳定不变 —— 重启、换群、隔多久都是同一个值
- **换 AppID 就全变** —— 连 `group_openid` 和已订阅的数据一起失效
- 反推不出 QQ 号
- 群消息里的 `member_openid` 和私聊的 `openid` **是同一个值**（实测）

怎么拿到自己的 openid：`uv run python scripts/test_c2c.py --listen`，
然后在群里 @ 一次机器人，脚本会打出 `✓ 抓到 openid: ...`（需先停掉机器人）。
或者先不配白名单跑一次，从 `notify_targets` 表里读。

三条设计约束：

- **绝不回落到群消息**。C2C 发不出去只记日志。宁可少一条通知，
  也不把错误刷进群。
- **同类消息按 key 冷却 30 分钟**。RSSHub 一挂是所有源一起挂，
  不冷却就是 DM 风暴（实测 5 个源会连发 5 条一模一样的通知，冷却后只发 1 条）。
  配图失败用的是 `imgfail:<群>` 这一个 key，**不带条目** —— 一条资讯 4 张图
  全挂只会报 1 次。代价是 30 分钟内的后续失败只进日志。
- **撤了管理员就摘掉**。自动登记模式下，某人若在登记表里但下次说话时
  角色已不是 owner/admin，会把他删掉 —— 否则被撤权的人会一直收到私聊。

想单独验证这条链路，用 `scripts/test_c2c.py`（裸 HTTP，不占机器人的
WebSocket 会话，可以和机器人同时跑）：

```bash
uv run python scripts/test_c2c.py            # 用库里登记的管理员 openid 发一条
uv run python scripts/test_c2c.py --listen   # 自己连网关抓 openid（需先停掉机器人）
```

### 指令面板只留三个入口（客户端输入框打 `/` 弹出）

官方支持配置「指令面板」，用户在 QQ 里打 `/` 会看到可用指令，点击即填入输入框。

**面板只有三个元素：`rss` / `new` / `help`。** 原因：面板实测是**平的、不能嵌套**
（见下），11 个元素挤在一起之后再加功能就没地方放了。所以面板只负责把人领进门，
订阅 / 退订 / 列表 / 搜索这些全收进 `/rss` 的按钮卡片里
—— 面板做不到的层级，消息里的按钮做得到。

- **手工配**：开放平台 → 发布设置 → 功能配置 → 指令配置面板
  - 配完**必须扫码确认修改**，只填不确认 = 不生效（API 查也是 0 个面板，
    客户端打 `/` 显示「这里还没有指令」）
  - 「使用场景」要勾 **QQ群**，**不能勾「消息列表」**
  - 已提交审核的指令改不动，要先删除再重新配置
- **脚本配**（可复现、可进版本控制）：

```bash
uv run python scripts/setup_panel.py --list      # 只读，先看现有的
uv run python scripts/setup_panel.py --create    # 创建群聊面板
uv run python scripts/setup_panel.py --update <panel_id>
uv run python scripts/setup_panel.py --delete <panel_id>
```

脚本内置官方字数校验（元素名 ≤14、描述 ≤30、单面板 ≤20 元素）。
⚠️ 官方限制的是**显示宽度不是字符数**，中文按 2 算 —— 16 个汉字的描述宽度已 32，
按字符数校验会放行，到接口才回 `30013`（而这个码文档写的是「超出数量限制」，
很容易误判成元素太多）。`validate()` 用 `_width()` 按官方口径算。

#### 面板能分组吗？不能。别把「菜单」和「面板」搞混

QQ 官方机器人有**两个容易混淆的东西**：

| | 指令面板 `/v2/panels` | 自定义菜单 `/v2/menu` |
|---|---|---|
| 在哪显示 | 输入 `/` 或 @机器人 拉起 | **只在「C2C 单聊」窗口底部** |
| QQ 群里 | ✅ 有（`scope=group`） | ❌ **不显示** |
| 能不能嵌套 | ❌ **平铺** | ✅ `sub_menu_items`，最多 5 项，**只有一层** |
| 元素类型 | `command` / `link`（**只有两个**） | `switch` / `send_message` / `link` / `menu` |
| 上限 | 20 元素 / 面板、20 面板 / 机器人 | 10 项 |

所以：**「QQ 机器人的菜单不能嵌套」是错的**，「**指令面板**不能嵌套」才是对的。
自定义菜单能嵌套一层（`sub_menu_items`，二级不支持 `menu` 类型，所以不可能更深），
但**它只在单聊窗口底部出现** —— 机器人主要活在群里的话，这条路用不上。

（上表是官方文档 `server-inter/menu-panel/` 及其 `autogen/api/v2_menu.*`、
`autogen/api/v2_panels*` 的原文结论，非推测。）

**指令面板是平铺的，没有子菜单**（2026-10-16 实测，`scripts/probe_panel.py` 可复跑）：

| | |
|---|---|
| 元素类型 | 只有 `command` 和 `link` 两种，**没有第三种** |
| 嵌套 | 塞 `children`/`items`/`sub_items` 会返回 **200 但被静默丢弃** |
| 上限 | 单面板 20 元素、单机器人 20 面板；name ≤14 / desc ≤30（显示宽度） |

两个判读要点：

- **「接口返回 200」不等于「存下来了」**。嵌套字段不报错也不生效，
  必须回读 `GET /v2/panels/{panel_id}` 比对。
- **错误码 30015 和 30016 的分界**：30015「元素类型不合法」= 这个类型不存在；
  30016「必填字段缺失」= 类型存在、只是还差字段。探 schema 全靠这个区别，
  分不清就会把「存在但缺参数」误判成「不支持」。
  （`link` 就是这么挖出来的 —— 它的必填字段名就叫 `link`。）

所以指令多了只能靠**加前缀命名**（`imas-news`）在视觉上分组。

想做真正的二级菜单，得在消息里带 `keyboard` 按钮 —— SDK 支持
（`post_group_message` 的 `keyboard` 参数，`action.type=2` 的按钮点击即发一条指令，
走现有群消息通道，不需要新 intent）。代价：菜单本身是一条消息，占主动消息配额；
面板是客户端 `/` 补全，不占配额。

**实测的面板数据形态**（服务端的行为，别按直觉假设）：

| | 服务端实际存/返的 |
|---|---|
| 指令名 | **裸名**，`/sub` 会被剥成 `sub`；客户端点击时自己补 `/` |
| `only_admin` | 为 `false` 时**整个字段省略**，回读是 `None`（不是 `false`） |
| 描述 / 顺序 / `target_type` | 原样保留 |

`compare_items()` 对前两项做了归一化。不归一的话会报出
「缺少 /sub、多出 sub」「list 的 only_admin 不一致」这类**假差异**，
把真正的问题淹掉。
并会先发一条只读的 `GET /v2/panels?scope=group` 确认 host 与参数，再动任何东西。

⚠️ 指令面板是较新的能力（约 2026-08 起），**需要较新版 QQ 客户端**才显示，
手机版优先、桌面版可能延后。**「接口成功但客户端看不到」属于灰度期的正常现象**，不是配错了。

选中「每条单独发一条图文」而不是「多条合并成一条摘要」，是因为**一条图文消息只能带一张图**：
官方 `media` 字段只接受单个对象，传数组直接 `400 请求数据异常`（实测确认）。
合并摘要就带不了图，所以改成逐条推送。

三个关键设计：

1. **首抓只建立 baseline，不推送**。否则一订阅就把该源最近 20 篇全倒进群里。
   去重靠 `seen_entries` 表 + 条目 guid（退化到 link，再退化到标题+时间哈希）。
2. **失败退避**。抓取失败的订阅同样更新 `last_polled_at`，等于退避一个间隔再重试，
   错误记在 `last_error`，`/list` 里会带 ⚠ 显示。
3. **配图失败自动退回纯文字**。图片抠不到、或 QQ 拉不到那张图（源站挂了、防盗链、太大），
   都不会让这条新闻丢失，会降级成纯文字再发一次。

## 推送文案

每条推送是「源名 / 标签 / 标题 / 摘要 / 链接」，摘要来自 RSS 的
`<description>`（Atom 是 `<summary>`）：

```
📰 少数派
· 某篇文章的标题

  这里是摘要正文，HTML 标签会被剥掉，超长截到 800 字
  https://sspai.com/post/12345
```

- **标题和正文之间隔一个空行。** 推送走的是纯文本，单换行读起来就是
  「标题紧贴着正文」一坨，空行把它切成两段。
- **摘要常常就是标题本身**（很多源的 `<description>` 直接放标题），这种会被
  自动去掉 —— 正文那行**和空行**一起不加，不会留个孤零零的空行。
- 关掉摘要：`.env` 里 `PUSH_SUMMARY=false`，退回「源名 / 标签 / 标题 / 链接」。
- 摘要长度用 `.env` 里的 `SUMMARY_CHARS` 调，**默认 800 字**。别调到 1200 以上 ——
  整条消息有 1500 字的上限，再高会把链接挤出去。
- **标签那行只有偶像大师那个源有**，见下面「偶像大师 NEWS 的企划 / 分类标签」。

## AI 摘要（可选，按源开关）

RSS 的 `<description>` 只是一段导语，**长度由源决定**。实测同一时刻 10 个路由：

| 少数派 | Solidot | 36氪快讯 | V2EX | Hacker News |
|---|---|---|---|---|
| 3914 字 | 368 | 162 | 93 | **32** |

V2EX / Hacker News 只给了标题，光靠 feed 永远拼不出正文。打开 AI 摘要后，
推送会变成：

```
📰 TechCrunch
· OpenAI 发布 GPT-7
  模型会写 3~5 句中文摘要，说清楚发生了什么、为什么值得看。
  https://techcrunch.com/...
```

**不附原标题** —— 曾经附过一行 `原题：…`，实测一条消息里标题/原题/摘要/链接
四段，群里一屏放不下，而原题的信息量最低。

开启方式（**默认全关**，因为会按次计费）：

```bash
DEEPSEEK_API_KEY=sk-...
DEEPSEEK_MODEL=deepseek-flash      # 默认值，可省
```

```text
/sub /hackernews/best 60 --ai     订阅并打开
/ai 2 on                          给已有的第 2 个源打开
/ai                               列出现在哪些源开着
```

- **默认只用 RSS 的 `<description>`，不去抓文章页**（`AI_FETCH_ARTICLE=false`）。
  很多源的导语本身就是全文（少数派 3914 字），再抓一遍是白花一次请求和几秒延迟。
  只有 V2EX / Hacker News 这种「导语只有标题」的源才值得设 `AI_FETCH_ARTICLE=true`。
  开了之后抓不到正文（付费墙 / JS 渲染 / 反爬）也会静默退回导语，照样翻译标题。
- **默认关掉模型的 thinking**（`AI_DISABLE_THINKING=true`）。DeepSeek 的 thinking
  默认开着且档位是 high，摘要这种抽取式任务不需要推理链 —— 开着多花 output token
  还每次多等 2~5 秒。顺带：**thinking 模式下 `temperature` 是无效的**。
- **模型名要对着官方文档核**：`deepseek-chat` 已退役，现在是 `deepseek-flash`
  （默认）和 `deepseek-v4-pro`。写错不会报错，只会静默退回 RSS 文案。
- **同一篇文章只付一次钱**：结果落库缓存，`/new` 重读、别的群订到同一篇都命中缓存。
- **日上限 `AI_DAILY_LIMIT`（默认 200，全局计）**，超了自动退回 RSS 文案。
- 模型走 `DEEPSEEK_BASE_URL`，任何 **OpenAI 协议兼容**的端点都行；
  **不要让它走 `MEDIA_PROXY`**（国内直连 0.2 秒，走代理反而更慢）。

想先确认某个源能不能抓正文：`uv run python scripts/probe_ai.py <文章URL>`，
加 `--call` 才真的调模型。

## 偶像大师 NEWS 的企划 / 分类标签

订阅 `/idolmaster/news` 时，推送的源名下面会多一行标签：

```
📰 NEWS | アイドルマスター
【灰姑娘】【演出/谷子】
· 【シンデレラ】＼明日まで🍎／「Apple of my アイ」現地チケット最速先行は…

  プロデューサーの皆さん、こんばんは！…
  https://idolmaster-official.jp/news/01_20131.html
```

为什么需要它：**RSS 里根本没有「企划」这个属性**（RSSHub 只把分类映射出来，
而且给的是日文原名 `グッズ`）。所以这一行是 `idolmaster.py` 自己调官网
CMS API 补的，一次请求同时拿到企划和分类。

**企划（7 个）**

| code | 标签 | 指 |
|---|---|---|
| `IDOLMASTER` | 本家 | THE IDOLM@STER（765）|
| `CINDERELLAGIRLS` | 灰姑娘 | シンデレラガールズ |
| `MILLIONLIVE` | 百万 | ミリオンライブ！ |
| `SIDEM` | 男人 | SideM |
| `SHINYCOLORS` | 闪彩 | シャイニーカラーズ |
| `GAKUEN` | 学马 | 学園アイドルマスター |
| `OTHER` | 其他 | その他（ヴィアラ等）|

**分类（11 个）**

| code | 标签 | 日文原名 |
|---|---|---|
| `GOODS` | 谷子 | グッズ |
| `LIVE-EVENT` | 演出 | ライブ・イベント |
| `COLLABO-CAMP` | 联动 | コラボ・キャンペーン |
| `LIVESTREAM` | 直播 | 配信番組 |
| `CD` | 音乐 | ミュージック |
| `GAME` | 游戏 | ゲーム |
| `RADIO` | 广播 | ラジオ |
| `MEDIA` | 媒体 | メディア |
| `ANIME` | 动画 | アニメ |
| `BOOK` | 书籍 | ブック・コミック |
| `OTHER` | 其他 | その他 |

两个 code 名不副实，所以**不是照着 code 直译的**：`CD` 的日文原名是
「ミュージック」（音乐，含数字发行和主题歌）；`LIVE-EVENT` 是
「ライブ・イベント」，涵盖演唱会**和**线下活动（快闪店、见面会、上映会）。

**一篇文章可以挂多个企划、多个分类**（实测 180 篇里 21 篇多企划、74 篇多分类），
这时用 `/` 连起来：

```
【本家/灰姑娘/百万/男人/闪彩/学马/其他】【演出/谷子】
```

这也解释了为什么**订一个源就够**：全企划通稿会同时出现在每个企划路由里，
订 7 个企划路由的话同一条要推 7 遍（实测推 84 条、去重后只有 65 条），
而且 7 遍的标签一模一样。

- 关掉：`.env` 里 `IMAS_TAGS=false`。
- 看标签对不对：`uv run python scripts/probe_imas.py`（**不发消息**），
  加 `--raw` 看 CMS 原始字段。
- 拿不到标签时**静默降级成不带标签**，不影响推送。

## 推送配图

条目正文里的图会被抠出来当配图（`rss.all_images()`，**最多 6 张**），支持 RSS 的
`description` 和 Atom 的 `content[]`，也能处理扩展名藏在 query 里的 URL。

- 发图是**两步**：先 `post_group_file(url=图片地址)` 拿 `file_info`，再
  `post_group_message(msg_type=7, media=...)` 发出去。
- **QQ 服务器自己去下载图片**（我们只给 URL），所以图片必须公网可达。
- 各源带图情况差别很大，实测：`/idolmaster/news` 12/12 条有图、
  `/v2ex/topics/hot` 2/9、`/36kr/newsflashes` 0/20。没图的源自动走纯文字，不用管。
- 关掉配图：`.env` 里 `ATTACH_IMAGES=false`，全部退回纯文字推送。

## 工作方式

```
QQ 群 @机器人 ──▶ GROUP_MESSAGE_CREATE ──▶ @ 过滤 ──▶ CommandHandler ──▶ SQLite
                                                                        │
FeedPoller（每 30s 扫一次到期的订阅）──▶ fetch_feed ──▶ 增量去重 ──▶ 逐条主动推送
                                                                    （有图走图文）
```

## QQ 2026 新协议（重要）

QQ 开放平台 2026 年起对群聊改用 **`GROUP_MESSAGE_CREATE`** 事件，`botpy 1.2.1` 不认识它，
网关会打一行 `ERROR botpy | _parser unknown event group_message_create.` 然后**把事件丢掉**。
症状是「机器人连上了、日志显示启动成功，但永远收不到任何消息」。
`src/qq_rss_bot/compat.py` 在建立连接前给 botpy 补上了解析器。

这个协议有三个后果：

1. **平台推的是全量群消息**，不是只推 @ 消息。群里任何人闲聊都会推过来（实测发「111」也推），
   所以 `bot.py` 必须自己筛 @，否则机器人会对着所有聊天乱回。
2. **报文里没有 `mentions` 字段**。实测 payload 的 `d` 里只有
   `author / content / group_id / group_openid / id / message_scene / message_type / timestamp`，
   @ 是以明文 `@显示名` 混在 `content` 里的。因此 `is_bot_mentioned()` 只能退化到字符串匹配。
3. 被动回复所需的 `msg_id`（`d.id`）仍在，`message.reply()` 正常工作。

**@ 有三种形态，都得认**：

| 形态 | 出现在 | 正文里长什么样 | 报文有 `mentions` 吗 |
|---|---|---|---|
| 显示名明文 | 手工 @ 机器人 | `@猪排爱好者 /ping` | 没有 |
| `openid` 占位符 | **指令面板按钮** | `<@C371C51BA906A22E4...> /help` | **有，且带 `is_you`** |
| 老数字占位符 | 老协议 | `<@!123456> /ping` | — |

判据优先用 `mentions[].is_you`——平台直接标了「这个 @ 就是你」，是唯一精确的依据。
有 mentions 但没一个 `is_you`，就说明是在 @ 别人，直接否定。

中间那种最容易踩：占位符里是 **32 位十六进制 openid**，不是 QQ 号。
正则若写成 `<@!?\d+>`（只认数字）就一条都匹配不上，
症状恰恰是「**面板完美显示，点了却毫无反应**」——而且丢在 DEBUG 级日志里，
从外面完全看不出原因。排查这类问题先把 `LOG_LEVEL=DEBUG` 打开，
`compat.py` 会把原始报文打出来。

**已知局限**：只有拿不到 `mentions` 字段时才会走到字符串匹配那一层，
此时有两种误判：
1. 显示名前缀：机器人叫 `bot` 时，`@bot2 hi` 会被误触发；
2. 占位符：`<@某队友openid> ping` 这种「@ 别人 + 恰好跟一个裸指令名」会被误触发。

**另注**：`mentions[].username` 会随机器人改名而变，别拿显示名做长期判据。要规避就在群设置里把
「机器人可获取的群聊消息范围」改回「仅接收 @ 机器人消息」，这样平台只推 @ 消息，
机器人就不需要自己筛了。

## 主动消息（RSS 推送的前提）

RSS 机器人的核心是「没人说话时主动推一条」，这依赖两件事：

1. **群内开关**：手机 QQ → 群设置 → 群机器人 → 你的机器人 → 打开
   「**机器人主动在群聊内发言**」。不开的话被动回复一切正常，但定时推送**全部静默失败**。
2. **机器人必须在线连着 gateway**。官方文档明确要求
   「发送消息接口要求机器人需要链接到 websocket gateway 上保持在线状态」，
   所以机器人进程不能停。

验证方式（不占用机器人的 WebSocket 会话，可并行跑）：

```bash
uv run python scripts/test_push.py                          # 推一条文字
uv run python scripts/test_push.py --route /idolmaster/news  # 从路由取首图推图文
uv run python scripts/test_push.py --image <图片URL>
```

**图片推送**同样验证过（HTTP 200）。QQ 支持直接给图片 URL，由 QQ 服务器自己去下载，
不需要本地中转，代价是多一次 `/files` 上传调用。

实测这个群是通的，返回 HTTP 200。官方频控：群聊认证后 60 qpm（机器人维度）、
20 qpm（单群维度）、**每群每天 1000 条**，对 RSS 推送完全够用。

## 可靠性

**推送语义是 at-least-once：先推送，成功了才把条目标记为已见。**

这样才有「网络一断也不丢新闻」的性质——推送失败的条目留到下个周期重试
（代价是延迟，不是丢失）。曾经的反例是在推送**之前**就标记已见，
结果网络中断时那批新闻已算见过、永远不再推，且没有任何日志。
`scripts/smoke.py` 里的 `[4.56]` 就是这条的回归测试。

只有**超出 `MAX_ITEMS_PER_PUSH` 上限**的条目是「有意丢弃」——那批直接标记已见，
不会反复重捞（否则一批来 50 条会永远卡在前 5 条上）。

**但这个机器人的可靠性等于它所在机器的可靠性。** 实测一小时内的运行环境：

| 现象 | 次数 | 影响 |
|---|---|---|
| DNS 解析失败（`api.sgroup.qq.com`） | 8 | 推送失败，下轮重试 |
| WebSocket 异常断开（1006） | 4 | botpy 自动重连，全部成功 |

网络断的同时事件循环还可能整个停摆：实测有个订阅 15:25 到期，直到 15:29 才被抓
（日志里伴随一次 1006 断开）。**笔记本合盖睡眠会冻结事件循环**，
这期间不抓取也不推送，醒来后才补。

所以：**要 7×24 稳定推送，别放在会睡眠的笔记本上**，换一台常开的机器
（VPS / 家里的服务器 / 树莓派）。放笔记本上就只能接受「醒着且网络好时才推」。

## 已知限制

- **主动消息配额**：群聊认证后 60 qpm（机器人维度）、20 qpm（单群维度）、
  **每群每天 1000 条**。程序内自设上限默认 900，留余量给回执/提示。
- **C2C（私聊）只用于发出错通知**，不做指令交互。私聊按官方文档是
  **每用户每天 1000 条**（另有第三方文档说每月 4 条，与官方不符）。
  实测群消息里的 `member_openid` 可以直接发主动私聊，无需对方先建会话；
  但发送失败仍然只记日志、不回落成群消息。
- **`group_openid` 不是群号**，且只能从事件里拿。所以：
  - 机器人被拉群时通过 `on_group_add_robot` 立刻记录；
  - 如果该事件没收到，等群里有人 `@` 一次即可补上。
- **Python 版本**：锁在 3.11–3.12。3.14 上 botpy 1.2.1 未经验证（其依赖链较老）。
- 文本消息有长度上限，推送内容截断在 1500 字符。
- **一条图文消息只能带一张图**（官方 `media` 字段只收单个对象，传数组 400），
  所以推送和 `/new` 都是逐条发，做不了「多条合并成一条摘要」。
- **「多条消息合并转发」官方机器人 API 不支持**：botpy 的群消息出口只有
  `post_group_message` / `post_group_file`，`msg_type` 枚举
  （0 文本 / 1 图文 / 2 markdown / 3 ark / 4 embed / 7 富媒体）里没有合并转发。
  那是 **QQ 客户端协议**的特性，支持它的 NapCat / Lagrange / LLOneBot
  走的是非官方客户端协议，不是这条 API。
